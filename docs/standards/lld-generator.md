# 📐 Universal Low-Level Design (LLD) Generator Standard

This specification governs the authoring, structure, and validation of all **Low Level Design (LLD)** documents generated by `/brain-deliver`.

All LLD deliverables in `04-deliverables/lld/` MUST strictly follow this authoritative 3-pillar layout standard.

---

## 📁 File Naming & Directory Convention

LLD documents MUST be saved in:
- **Path:** `04-deliverables/lld/<feature-name>-lld.md`
- **Example:** `04-deliverables/lld/checkout-idempotency-lld.md`
- **Document Title Format:** `# LLD - {FEATURE_TITLE_UPPERCASE}`

---

## 🏗️ Mandatory 3-Pillar Section Structure

Every LLD document MUST include the following exact sections and headings:

```markdown
# LLD - {FEATURE_TITLE_UPPERCASE}

# I. Introduction and Scope Sections

### 1. Objective Overviews
Comprehensive objective narrative describing the feature, business background, technical goals, and system impact.

**Scopes:**
1. [Endpoint / Interface 1]: Detailed description of enhancement or new implementation
2. [Endpoint / Interface 2]: Detailed description of enhancement or new implementation
3. [Sequence Diagram 1]: Detailed description of flow logic
...

#### Scope Metrics & Impact Quantification:
| Metric Dimension | Classification | Count | Impacted System / Location | Details / Component Scope |
| :--- | :---: | :---: | :--- | :--- |
| **1. Number of new or enhanced features/functions** | New | 0 | - | None |
| | Enhanced | 1 | `[Service Name]` | Description of enhancement |
| **2. Number of new or enhanced pages/UI views** | New | 0 | - | None |
| | Enhanced | 1 | `Frontend Web / Mobile` | Description of UI changes |
| **3. Number of new or enhanced inputs** | New / Enhanced | 0 | - | Read-only / Form controls |

### 2. Glossaries
| Term / Acronym | Definition & System Ecosystem Context |
| :--- | :--- |
| **[Term 1]** | Description of domain term and contextual meaning |
| **[Term 2]** | Description of domain term and contextual meaning |

# II. Solution Details Sections

### 3. Impacted Objects
| Microservice / Component | Modification Area & Technical Impact |
| :--- | :--- |
| **`[service-name]`** *(Backend Service)* | • Handlers/usecases modified.<br/>• Endpoints or RPC methods impacted. |
| **Database** *(RDBMS)* | • Table `[table_name]` : Added column `[col_name]`. |
| **Cache Store** *(No-SQL / Redis)* | • Key `[cache_key_pattern]` : Stored data structure and TTL. |
| **Message Broker** *(Queue / Topic)* | • Topic `[event.topic.name]` : Event payload changes. |

### 4. Sequence Diagrams & Flow Descriptions
- Embedded complete PlantUML sequence diagrams (`@startuml ... @enduml`).
- Explicitly highlight enhancement blocks using `group #F8D4AF ENHANCEMENT [...]`.
- **Mandatory Step-by-Step Flow Descriptions:** Directly beneath each sequence diagram block, provide an exhaustive, numbered narrative breakdown (`##### Step-by-Step Flow Description:`) detailing:
  1. User / Calling Channel initiation & endpoint path.
  2. API Gateway forwarding & header authentication.
  3. Internal service-to-service gRPC / REST communications.
  4. External surrounding system inquiries (Payment Gateways, Identity Providers, SaaS, etc.).
  5. Database / Cache operations & business logic branching.
  6. Return payload assembly and Frontend UI rendering / action execution.

### 5. Technical Flows & Surrounding Systems
- Concise system-to-system Technical Flows (Only system-to-system communications, excluding DB/cache).
- Categorized Surrounding Systems list per flow:
```text
[Feature Name] - [Flow Name]

1. Frontend Web -> API Gateway
    GET /api/v1/resource
2. API Gateway -> Core Service
    GET /api/v1/resource
3. (If condition)
    Core Service -> External System
    POST /v1/external-action

Surrounding:

1. External System
```

### 6. Application Interfaces
- Links to authoritative API contracts / OpenAPI specifications.
- Request & Response JSON schemas with field types and validation rules.
- Protobuf schema definitions for gRPC services.

### 7. Data Designs
- ERD PlantUML snippets highlighting new/modified columns with `<back:#F8D4AF>column_name : TYPE</back>`.
- JSON schema structures for Cache keys and Event Broker payloads.

### 8. Security Measures
1. **Authentication & Token Integrity:** Bearer JWT authorization, token validation, and claim verification.
2. **Access Control & RBAC:** Role and permission validation per route.
3. **Input Validation & Tampering Protection:** Server-side price calculation, strict DTO schema validation, and parameter sanitization.
4. **Rate Limiting & Abuse Prevention:** Throttling and idempotency protection.

# III. Closure Section

### 9. References
Authoritative documentation and design reference links:
1. **[Product Requirements Document (PRD)] [{PRD_TITLE}]({PRD_URL})**
2. **[Architecture / UI Design] [{DESIGN_TITLE}]({FIGMA_OR_MIRO_URL})**
3. **[Issue / Task Tracker] [{TICKET_ID}]({TRACKER_URL})**
```

## 📊 Mandatory GFM Markdown Table Standard (Zero ASCII Box Drawing)

All tables inside LLD documents (such as **Impacted Objects**, **Glossaries**, **Error Code Matrices**, and **Scope Metrics**) MUST be authored in standard **GitHub-Flavored Markdown (GFM)** tables.

- **BANNED:** Never use Unicode/ASCII box drawings (`┌───┐`, `├───┤`, `│...│`, `└───┘`) inside markdown documents or code blocks as they break on varying viewport sizes.
- **MANDATORY GFM TABLE FORMAT:**
  ```markdown
  | Component / Service | Modification Area & Technical Impact |
  | :--- | :--- |
  | **`order-service`** *(Backend)* | • `internal/usecase/checkout.go` : Added idempotency lock.<br/>• `config/routes.go` : Added route `/v1/checkout/orders`. |
  | **Database** *(PostgreSQL)* | • Table `orders` : Added column `idempotency_key VARCHAR(64) UNIQUE`. |
  ```
- **MULTILINE CELLS:** Use `<br/>` for line breaks and sub-bullets inside table cells.
- **ALIGNMENT:** Explicitly define column alignments (`:---` for left-aligned text, `:---:` for centered codes/metrics, `---:` for numeric values).
